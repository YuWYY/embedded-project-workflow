# Sample statistics feature handoff

This is an original input fixture for an independent feature implementation. The baseline deliberately contains only valid idle task bodies and object-creation checks. Generated ST/Arm/FreeRTOS sources and native build products belong under an isolated `tool-trials` work directory, outside this source repository, and keep their vendor licenses.

The next stage is to implement a producer that sends the cyclic sequence `10,20,30,40,50,60,70,80,90,10,...` every **10 RTOS ticks** through `SampleQueue`. The consumer maintains statistics over the latest **8 successfully received samples**. Failed queue sends must be counted separately from received samples and must not enter the statistics window. The feature agent should define the useful statistics and observation interface in its implementation notes and test the warm-up and rolling-window behavior. This baseline does not implement those behaviors.

The shared portable statistics core is to be implemented by the feature agent in `examples/common/rolling-stats/epw_stats.c` and `epw_stats.h`. Its public contract uses caller-allocated `epw_stats` state and `uint32_t` storage, capacities 1..16, no heap, a `uint64_t` running sum, and C/C++ compatible declarations. `epw_stats_result` contains `uint32_t count, minimum, maximum, mean`; integer mean truncates toward zero. API: `bool epw_stats_init(epw_stats*, uint32_t *storage, uint32_t capacity)`, `bool epw_stats_push(epw_stats*, uint32_t)`, `void epw_stats_reset(epw_stats*)`, and `bool epw_stats_read(const epw_stats*, epw_stats_result*)`. Reading an empty initialized window returns false and zeroes the result. Follow the independent host contract tests supplied for this interface. This baseline has no core implementation or compiled core source; the feature stage must integrate its final core into the actual Keil build and keep STM32/RTOS details in the task-facing files.

| Native object | Required contract | Implementation owner |
| --- | --- | --- |
| `SampleFeed` | First configured task; Normal priority; static stack **256 32-bit words = 1024 bytes**; external `SampleFeed_Entry` | `Services/Sampling/sample_feed.c` |
| `StatsWorker` | Second configured task; Normal priority; dynamic stack **384 32-bit words = 1536 bytes**; external `StatsWorker_Entry` | `Domain/Statistics/statistics_worker.c` |
| `SampleQueue` | Static queue of **12 uint32_t elements = 48 payload bytes** | Native generated declaration and creation |

`sample_statistics.ioc` owns task names, order, priorities, allocation policy, stack sizes and queue element capacity. CubeMX owns declarations, attributes, and object creation in `Core/Src/app_freertos.c`. Keep its native creation order. User code may check handles after creation via the existing `RTOS_THREADS` user region. External task entry points make a missing user implementation a link failure. Do not add tasks or recreate these objects elsewhere. All raw sample transfer between tasks must pass through `SampleQueue`; no shared raw-sample array or direct shared sample variable may bypass it. Statistics state belongs in `Domain/Statistics`; sampling schedule and sequence belong in `Services/Sampling`. Do not move business logic into `main.c` or non-user generated regions.

The baseline uses STM32G474RE/LQFP64, HSI at 16 MHz, TIM6 for the HAL time base, CubeMX **6.18.1**/DB **6.0.181**, STM32CubeG4 FW **1.6.3** with its ST CMSIS-RTOS2 wrapper/FreeRTOS **10.3.1**, Keil STM32G4xx_DFP **2.0.0** and **ARMCC 5.06 update 7 build 960**. Both static and dynamic RTOS allocation remain enabled. This is a mixed-allocation project; it is not a claim that the whole system avoids the heap.

Use `prepare.py --help` for baseline reproduction. Supply the five installed tool/package paths explicitly and new, separate `--work-root` and `--reports` directories outside the repository. The script reuses existing adapter helpers without changing their code or API. It invokes native CubeMX generation, integrates the original user files and documented user region, adds those two sources/include paths to the generated Keil project, selects the installed ARMCC5 compiler, disables empty user-program hooks, and runs a native rebuild. Source hashes, process records, generation command script, logs, linked-entry ownership and MAP sizes are preserved in the report directory. It only prepares the baseline; later user implementation must have its own fresh source-bound validation.

Do not install or download tools/packages, flash, start debug, access serial ports, operate hardware, or push repositories. Native compilation and MAP inspection establish build/link properties only; target scheduling, queue behavior, timing, stack watermarks and physical operation remain unverified until separately authorized and measured.
