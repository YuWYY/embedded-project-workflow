## 历史真实 Vivado 2025.1 验证

- Clocking Wizard：50 MHz 输入、100 MHz 输出；从配置源修改到 125 MHz 后再生成；从空目录重建 125 MHz。三阶段均完成输出产品、XSim、IP OOC 和顶层综合；每阶段检查 400 个周期与两次复位。
- XPM 异步 FIFO：16 位、512 配置深度、80/100 MHz；独立参考队列核对 3600 次接受、3500 次输出和 100 次合法复位丢弃。覆盖 full、empty、流量及暂停。
- 受控数据损坏：只反转输出 bit 0，检查器发现 `0x1357` 与 `0x1356` 不一致并失败；编译展开成功，负例不是语法错误。
- 完整重建入口曾从新目录追加运行五个阶段，均完成。开发阶段与完整复验合计 14 次 Vivado 调用，包含三次真实失败，不是一次无误运行。

三次开发失败分别为不存在的 IP 属性、XPM 启动复位与内部初始化重叠、再生成后旧 OOC 任务状态。修复对应测试或流程并重跑，保留失败结论。没有为了清零警告添加宽泛时序例外。

未覆盖：布局布线、完整板级约束与时序收敛、bitstream、下载、板测、时钟相位扫描、随机复位及物理亚稳态。XPM 自动 Gray-code CDC 豁免与模块接口未配置板级 I/O delay 均需在真实工程中结合报告处理。示例参数不属于 Skill 的通用默认值。

## 本轮真实 STM32/CubeMX 试用（2026-09-28）

**状态：生成、主机测试及构建验收通过。** 使用用户指定工程的隔离工作副本，完成基线检查、四次实际 CubeMX 调用、两轮修复后的完整生成及最终回归。工具为 CubeMX 6.18.1、STM32Cube G4 FW 1.6.3、ARMCC 5.06 update 7 build 960、STM32G4xx_DFP 2.0.0；构建始终使用工程原有 `normal` 配置。

| 实际阶段 | 结果与处理 |
|---|---|
| 第一次生成 | 隔离复制时误排除了 `.uvoptx`，生成器更新旧 Keil 工程出现 `FileNotFoundException`。进程退出0，但生成不完整，判定失败；恢复必要配套结构并关闭本轮不需要的调试下载选项。 |
| 恢复配套文件后重试 | 完整生成暴露了旧工程在生成区外维护的时钟、IRQ、FreeRTOS 钩子、HAL 模块与内存边界配置，随后构建出现7个链接错误。没有将这些历史边界问题算作本次 Skill 制造的固件缺陷。 |
| 修复后的完整生成 | 基础配置修回 `.ioc`，必要入口放到受支持的用户扩展位置；用户维护的 Keil 构建入口及 scatter 文件负责自定义编译宏和布局，接入工具生成的源码。实际构建通过。 |
| 再次完整生成与保留核查 | 用户构建工程、链接脚本、`.ioc`、ADC、IRQ 和主入口字节稳定；FreeRTOS 文件只有结束标记缩进归一化，两个所需钩子各保留一份。无需再次手工补回接入，最终完整回归通过。 |

最终项目引用检查、完整主机测试 runner 和构建 wrapper 均退出0；主机测试包含58项 JavaScript 测试及既有固件逻辑测试。干净目标构建为0错误、1个已有的不可达语句警告；原生 Keil 返回的警告状态与 wrapper 成功状态分开处理。构建记录确认源码在构建期间稳定，链接布局契约通过。独立技术复核检查了应用任务强符号、IRQ 接入及 CCM/SRAM 布局，不仅检查文件存在或编译完成。

原始工程4966个文件、旧 Skill 及历史材料743个文件在最终哈希复核中均未增加、删除或改变。没有连接硬件、下载、串口或带载操作。完整工程、原始日志及固件留在本地；公开说明只保留可分享的过程与结果，因此它不是可从本仓库复建的固件案例。

仅针对这些观察修改 CubeMX 指南：按用途保留生成器配套文件；结合日志、产物和差异判定生成；核查相关 HAL/业务编译宏和链接布局的含义；已证实构建元数据会被覆盖时明确用户构建入口。没有要求所有项目拆分构建，也没有将本轮完整验证清单变成每轮工作门禁。

## 本轮公开 Vivado 入口复验（2026-09-28）

[五阶段摘要](../examples/vivado/validation-20260928.json) 来自本轮公开入口的实际完整执行：三个时钟阶段、FIFO 正例和受控负例均达到预期，125 MHz 再生成与空目录重建的配置语义一致。源文件保留检查均通过，仿真计数与上述历史结果一致；这是一轮新执行，不能将其与历史14次调用合并成一次无误运行。

完整运行后发现 Windows PATH 中同时存在 Unix `vivado` 脚本与 `vivado.bat`。最终入口只修改了查找顺序，优先 `.bat` 再 `.exe`，随后实际通过 PATH 启动 Vivado batch 探针，核对2025.1版本及退出0。[后续验证记录](../examples/vivado/portability-followup-20260928.json) 保存完整运行版本和最终入口各自哈希，明确未再执行五阶段。RTL、Tcl和测试平台未因此改动。

原生 `-version` 曾打印版本却返回非零；接受的 PATH 验证使用显式 Tcl 完成标记与退出0。最终证据是“五阶段完整执行 + 一行启动器选择修改的针对性验证”，不声称最终脚本原样重跑了整个流程。

## 公开仓库的可重复检查

[发布脚本](../scripts/release.py) 校验文件白名单、SHA-256、Skill 元数据与相对引用、脚本语法及发行包成员/字节。`self-test` 在单独的临时副本中修改一个受清单保护的文件，要求校验非零退出；这验证“计算出的哈希差异确实进入失败判定”。它也核对额外文件与 ZIP 内容错误被拒绝。

这些检查不访问厂商工具或外部模型，不证明 Skill 的工程决策正确。公开 Vivado 入口的真实执行与后续修改验证已在上一节分别记录。
