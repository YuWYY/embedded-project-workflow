# CubeMX与配置所有权

仅在新建工程、基础配置修改、再生成或运行参数耦合时使用。遵循当前工具版本与芯片能力，不将某个系列的寄存器编码或GUI菜单直接套到其他系列。

用户预先配置的外设、中间件、接口和资源关系按[设计约定](configuration-contracts.md)处理；AI可以代配置，但不能用应用层另一套初始化绕过明确要求。涉及任务、队列等对象规划或静态/动态分配时，按需读取[FreeRTOS指南](freertos.md)，不默认把RTOS骨架全部手写在应用层。

先识别工程实际使用的生成器。经典CubeMX常以USER CODE标记保留扩展，CubeMX2可采用生成与用户代码分文件的结构；保护实际扩展边界，不强制迁移工具或改造成同一种目录布局。

## 读取足以决定本轮动作的材料

优先定位`.ioc`、现有初始化和应用入口、用户配置头文件、实际构建工程及相关硬件事实。确认外设句柄、IRQ名称和时钟来源，不从其他项目猜名字。已知芯片、接线、用途不要重复问。

新项目尚无用途时，只追问会决定采样/控制/资源分配的事项，例如测量还是闭环、信号量程/带宽、需要的通道和接口、是否使用RTOS。基础已知时可同时列出确定项和待决项，不让用户填写全部定时器比较值。

## 最少必要配置建议

按实际版本写软件位置，以下是类别而非要求每次重做的清单：

| 基础项 | 建议必须解释的内容 |
|---|---|
| MCU、封装、引脚 | 原理图/实装对应关系、外设实例与复用；已确定的硬件连线由AI整理 |
| RCC、Clock Configuration | 晶振/外部时钟实际类型与频率、目标时钟的需求依据、外设时钟来源；不要把HSE频率当任意性能旋钮 |
| DMA资源与传输属性 | 请求/通道映射、方向、数据宽度、增量、循环或普通模式，以及缓冲用途 |
| NVIC、RTOS | IRQ实际调用链是否使用RTOS API；优先级依据当前内核配置，而非固定套用数字 |
| 调试与工具链 | 所用IDE、编译器及工程源文件接入；不为采用本技能强制迁移工具链 |

格式：配置项、GUI位置、建议值、来源/用途、核对方式。只展示当前必要项。高级硬件模式是否支持由当前设备与工具能力确认，不能预设CubeMX一律支持或一律不支持。

## 分开“基础错误”和“有意的二次配置”

基础错误如实际晶振与`.ioc`不符、引脚复用错误、DMA请求连到错误外设：修正源配置再生成。默认先建议用户操作；明确代操作授权后才执行配置/生成。依赖这次修正的代码不能以手改覆盖区假装已完成，可先做不依赖生成结果的独立模块。

应用拥有的参数如PWM Hz、死区ns、控制给定：在自有配置集中修改，再由自有初始化/更新函数应用。生成值可以只是初始化占位，但必须满足：

- 占位初始化本身合法，不会在用户参数应用前意外启动目标功能。
- 启动调用链明确经过应用配置，故障/重启路径也不绕开它。
- 后续`MX_*_Init()`或其他写入者不会悄悄恢复旧值。

不要将“应用最终重配ADC序列/触发”误判为必须把所有动态参数迁回GUI；也不要用二次配置解释真实引脚、时钟或DMA映射错误。每个字段给出最终来源与生效时点即可，不额外制造一套配置审批系统。

## 修改频率、死区或采样参数

先确认实际外设时钟、倍频/预分频、计数方式、周期寄存器语义和死区编码。不同TIM/HRTIM的编码不通用。以物理量推导计数；无法推导的独立值说明原因并核对一致性。

仅检查本次变更影响的依赖：

- PWM周期、比较点、占空比边界、死区是否可实现。
- ADC触发位置、转换时长、相位覆盖和采样/控制分频。
- DMA批次事件间隔、复制截止时间及快速保护响应。
- 控制`dt`、离散积分/滤波系数、斜坡和按周期计数的超时。

不从一个寄存器数值变更推断所有物理效果已经验证。应用拥有的调参不要求重新生成；若确实需要改变基础时钟或资源映射，说明具体哪一项需要回GUI。

## 用户代码落点与启动

生成文件内使用工具原有的保留区域、回调或正式扩展点；自有APP/BSP模块承载主体逻辑。弱函数覆盖、回调注册或其他接入方式须核对当前实现，不假定创建同名函数就一定生效。

沿实际调用链检查基础初始化、用户最终配置、DMA准备、触发启动及功能使能顺序。需要同步采样时，“输出关闭但采样时基工作”可能是正常状态；不要让通用停机函数误停全部观测。输出状态与采样状态应依据用途决定，而非套固定序列。

## 重新生成验证

需要生成时，先保留可恢复基线，使用实际工具和匹配的工程配置。工具版本/固件包变化要单列，不能将未经请求的升级混入功能修改。若当前没有生成工具，仅提供待执行配置与接入方案，不能把手工编辑称为生成验证。

建立隔离副本时，区分生成器读取的必要配套工程文件与个人会话状态；按实际用途筛选，不按扩展名一律排除。必要文件含下载或调试选项时，在副本中保留生成所需结构并关闭本轮未授权的动作。

生成完成要结合日志、预期产物和实际差异判断。进程退出0不等于所有生成步骤成功；出现异常或部分产物缺失时，先查失败阶段，不把旧文件仍存在当作本次生成完成。

生成后检查相关差异和构建输入：

1. 用户保留区和自有文件是否仍在，生成器有无改名、删外设或改变初始化顺序。
2. 应用入口、IRQ/回调、RTOS任务和外设句柄是否仍连接。
3. 自有源文件、头文件路径、链接脚本和必要库是否仍进入真实构建；相关编译宏的含义、链接内存区域与边界是否仍符合工程要求，不能只检查路径存在。
4. 需要时执行目标工具链构建；运行参数生效只能报告到实际取得的证据层。

若生成器确实会改写无法保留的自定义构建元数据，可以明确一个用户维护的构建入口，并保持它与生成源码、头文件和必要工程资源的接入。说明两者各自负责什么，不维护两套互相覆盖的参数；已有可靠构建工程无需因此强制拆分。

生成前后对比是功能接入检查，不只是文件是否保留。只在本轮涉及生成边界时做这些检查，普通应用改动不重复生成全工程。

## 已有RTOS工程的窄适配入口

包内的 [cubemx_rtos.py](../scripts/cubemx_rtos.py) 提供 `doctor / inspect / plan / apply / verify`。它只支持已核实的 Windows、CubeMX 6.18.1、G4 1.6.3、ST CMSIS-RTOS2、ARMCC 5.06 u7 与 STM32G474RE 工程形态：按已有任务名称修改栈 words，保留分配策略；按已有静态 uint32_t 队列名称修改元素容量。它不是任意CubeMX工程导入器。

先只读检查工具和当前对象，再生成含单位、语义差异和源哈希的一次性操作计划。`apply` 前重新核对工程身份；人工改动使计划失效时，应分析当前差异并重新计划，不能覆盖新配置。IOC仍为参数来源，计划不是第二套工程配置。备份和IOC原子写入不表示多文件生成具有事务原子性。

适配器拒绝不支持的版本、字段形态、动态队列和不能确认的用户接入；不要绕过拒绝检查、猜字段或切换编译器。可以按上文通用方法做当前工程的人工分析，明确适配器未覆盖。生成和构建必须核对用户对象文件实际提供任务入口，不能由弱默认任务掩盖缺失实现。栈/队列容量与MAP只证明生成和链接属性，不证明运行栈水位或整个系统无堆。

机制依据：[STM32CubeMX官方说明](https://www.st.com/content/st_com/en/stm32cubemx.html)。菜单、CLI和支持能力需要随实际版本核对；不把本文作为工具命令手册。
