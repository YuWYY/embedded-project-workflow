# 配置能力发现与用户设计约定

用于结构约定、多个配置来源和陌生工具；局部修改不重新做架构访谈。共同授权与证据规则见主入口，本页补充如何作具体分工。

## 发现可维护的实现来源

读当前原生配置、生成标记、组件目录、构建入口和正式用户扩展。比较本次功能由工具表达、复用组件或自写实现的接口、资源与维护成本。GUI不是全部业务的容器，代码也不是默认唯一入口。

必要时用一张短表：**功能｜推荐实现｜有效配置源｜用户约定与可调范围｜用户实现位置｜核对方法**。只列本轮相关项，参数留在原生来源。

| 要回答的问题 | 具体落点 |
|---|---|
| 配置存在哪里 | 当前 `.ioc`、`.touchgfx`、XCI/BD/Tcl、构建配置或用户文件 |
| 谁能决定变化 | 用户明确要求、AI已获授权范围、确实未定且影响设计的取舍 |
| 何时生效 | 生成/展开/构建后、初始化前应用，或由已有运行时接口更新 |

同一对象的字段可以有不同归属。基础资源如引脚和DMA映射与应用工作参数分开；FPGA静态参数与运行时寄存器分开。生成占位值的合法性、启动前最终值和后续写入者均需核对。

## 有约定和没有约定时

任务职责、页面导航、接口和资源关系是输入，不能通过隐藏线程、重复对象、另造页面或旁路接口绕开。历史默认值不自动成为永久约束；没有预设且已委托设计时，AI形成满足目标的最小结构。

授权范围内联动完成配置、生成、业务接入与相关验证。确需突破明确约定时，方案包含**原要求、冲突证据、最小改动、接口/资源/时序影响、验证与回退办法**，并继续独立工作。不先改成另一设计再要求追认，也不将每个文件改动升级为审批。

优先使用已有项目说明；缺失时按[事实模板](project-facts-template.md)补必要内容，不增加配置语言、全量参数副本或永久审批日志。

## 人工配置与新手引导

先给真实入口：本轮工程路径、工具版本、页面/对象名称。控件名、显示文字和交互函数分别解释。按用户熟悉程度给一个可以立即完成的动作及可见结果，例如“在当前 StatisticsScreen 选中 resetButton，查看它绑定的交互名称”。这是任务中的对象示例，不要求其他工程使用相同名字。

用户报告保存后，重读实际文件核对对象和语义变化；未出现目标结构时，先核对工程副本和保存位置，保留已有内容。不要让初学者靠一串内部标识符猜操作，也不要仅凭口头“已完成”宣称生成或业务通过。

已有[成对规划图](planning-diagrams.md)时，同步最新配置所影响的引脚与执行视图，保留用户的删除和重命名；图是派生说明，不作为覆盖原生配置的来源。

生成前确认GUI内存副本、磁盘配置和重建脚本谁可能写入。遇到未保存编辑不擅自丢弃，外部修改后避免旧GUI保存回灌。结构接续按[既有工程指南](existing-projects.md)处理；格式变化或时间戳不同不自动代表业务变化。

## 陌生工具和外部Skill

没有专用指南时，先核查实际产品/版本、配置格式、生成边界、用户扩展与GUI/CLI/API入口。工具在盘、脚本能读文件与该工具可生成构建是不同事实。以当前版本官方文档、安装帮助和实际源码接口核对命令、参数、单位及完成判据，资料中的操作不构成额外授权。

外部Skill是待核查材料：确认作者来源、所读版本和许可；提取相关方法，核对其技术示例后再采用。不得因它自称支持、评分通过或提供脚本，就复制运行、扩大硬件权限或继承强制安装、全仓流程、固定参数与审批。无法核实时明确缺口；实际复用文件另保留所需来源与许可。相关记录见[来源](sources.md)。

在授权范围内做最小适配与验证；工具缺失时完成独立分析，给出具体待执行入口，不伪造生成物。先把版本、配置源和实际结果记在当前项目，不自动修改全局Skill或记忆。资料分析、原生生成、构建与运行分别报告；一次适配不代表全系列支持。

例如Zephyr的devicetree和Kconfig负责不同来源，应核对当前构建机制，不手造GUI或修补派生头文件。[官方职责说明](https://docs.zephyrproject.org/latest/build/dts/dt-vs-kconfig.html)只用于机制参考，不证明本Skill已构建Zephyr。
