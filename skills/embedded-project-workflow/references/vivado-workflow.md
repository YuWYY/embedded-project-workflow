# Vivado：配置源、生成产物与用户 RTL

用于Vivado IP/XPM/BD配置、生成、接入及相关回归。先按[IP选型](ip-selection.md)决定是否需要IP；简单自有RTL不必走IP生成流程。涉及板卡依据读[板级资料](board-evidence.md)，PS/PL与BD系统读[Zynq/MPSoC](zynq-mpsoc.md)，XSA下游或工具交界问题读[Vitis交接](vitis-handoff.md)。这些指南不声明完整Linux、多核、DDR或高速接口的已验证支持。

完整架构规划需交图时按[成对规划图](planning-diagrams.md)表达端口依据、主要并行模块及各自执行条件、时钟/复位范围和真实CDC连接。

## 识别实际工程

定位当前顶层、RTL/仿真源、XDC、XCI/BD、重建Tcl、工具/器件/IP版本及工作基线。使用工程属性和真实器件信息，不能由粗略型号前缀推断是否有PS。保留Project/Non-Project、RTL/BD等既有组织方式，不为采用本Skill强制迁移。

预设IP、时钟域、端口、握手、连接和资源范围按[用户设计约定](configuration-contracts.md)处理。参数在允许范围内可自主调整；替换IP若改变读延迟、复位或接口语义，先核对约定及适配代价。人工更新XCI/BD/Tcl后重读有效来源，不能用旧重建脚本覆盖新设计，也不一律要求把RTL工程改为BD。

核查安装的器件支持、IP版本和仿真库；许可检查只收集解决问题需要的状态，不把许可证内容或凭据写入报告。工具可用不等于IP配置已合法，仓库示例可生成也不等于当前板卡能使用。

## 三种参数不能混淆

| 类型 | 最终配置者 | 本次改变的后续动作 |
|---|---|---|
| 板级/资源：part、封装、输入时钟、管脚和电气标准 | 工程、约束及硬件事实 | 修正源配置，检查对应资源/约束与实现要求 |
| 静态设计：IP CONFIG、RTL parameter/generic、XPM宽度深度、静态时钟频率 | XCI/BD/重建Tcl或用户RTL中明确的一处输入 | Catalog IP按需重新生成；RTL/XPM重新展开、仿真或构建受影响设计 |
| 运行时：实际提供的CSR、AXI-Lite寄存器、DRP等 | 寄存器和接口契约 | 检查合法值、原子生效、握手、跨域及复位/停钟关系 |

一个功能可以同时有静态和动态参数。运行时能力须在IP中真实存在并正确启用；不能认为修改宏就能改变已下载硬件，也不要为纯静态参数机械新增命令接口、ACK或掉电保存。频率改变需联动真实时钟约束、分频、超时、接口节拍和相关模块，而非只改显示标签。

## 唯一配置源与可编辑范围

- 既有GUI工程可由XCI/BD维护IP设置，Tcl用于导出或操作；已有脚本工程可由重建Tcl维护参数，XCI记录生成结果。说明哪一处为准，不要求每项同时手工维护两套数据。
- XPM/推断模板没有必需的独立XCI；参数在用户RTL中并由真实库解释。不虚构GUI生成步骤。
- 用户逻辑放自有RTL、顶层和wrapper。不要直接修补IP生成HDL、仿真模型或DCP来掩盖配置源错误。需修改开源核心时保留固定上游版本和明确补丁，不把修改假称为纯配置。
- BD wrapper由Vivado管理时会随输出生成更新；复制为用户维护后，端口变化要由用户层更新。业务逻辑优先放外层，检查实际wrapper归属，不仅按文件名判断。
- 约束也有来源与作用范围。区分IP附带XDC/OOC时钟约束、顶层时钟、I/O和必要例外；不能通过大范围false path或降低DRC严重性掩盖设计问题。

## 建议、代配置和生成

先给出“功能、推荐IP、软件位置、关键参数、原因、核对方法”。默认由用户操作GUI；明确要求代操作时，优先用实际版本支持的原生Tcl，也可用可用GUI。已有授权继续有效。无法运行生成器时提供具体配置/接入步骤，标明未执行，不手造厂商输出冒充生成。

以下为按需动作，不是每轮强制流水线：

1. 读取当前配置和所需IP定义，确认参数属性与合法组合；避免从别的系列/版本猜CONFIG键。
2. 在明确配置源上创建或重新定制。`create_ip`本身不证明完整输出已生成；检查实际CONFIG、端口及目标器件。
3. 需要时生成output products，按原工程选用OOC或全局综合；不默认每次reset全部IP、清所有缓存或运行到bitstream。
4. 接入自有RTL/BD，检查数据和控制连接、复位极性/时序、时钟关系及约束。BD自动连接不能代替需求核对；`validate_bd_design`参数传播后检查最终配置。
5. 更新仿真源、库、源序和构建引用，执行本次相关的功能验证与构建，检查运行状态、计数和失败退出。

可核对的命令类别包括`get_ipdefs`、`get_ips`、`report_property`、`report_ip_status`、`generate_target`、`synth_ip`/OOC runs、`validate_bd_design`。这些不是可盲目粘贴的完整脚本；确认当前对象、工程状态、路径和实际版本再调用。

重建记录保留工具/器件/IP版本、CONFIG输入、第三方commit、源/约束入口及执行命令。`write_ip_tcl`适用于独立IP，BD使用`write_bd_tcl`；导出脚本还要包含实际依赖和资源文件，不能把导出成功当成空目录重建成功。

## 再生成与版本异常

生成前保留可恢复基线。生成后针对改动检查端口宽度/名称、延迟模式、wrapper、源文件/库引用、时钟复位和XDC的对象是否仍有效；保留了用户文件不代表它仍被编译或连接。

对locked IP先查状态原因：工具/IP版本、part改变、许可或输出缺失等不能一概归为升级问题。旧版static IP有完整可用产物时可能继续工作；无可用产物时比较匹配原版本、恢复对应产物或正式升级。不得用去掉版本号、伪造解锁或全量升级绕开兼容性判断。升级前保留基线，核查变更及端口/参数差异。

路径/旧缓存错误优先核对实际源引用。需要隔离复现时使用新的可写构建目录；不删除现用工程来获得“干净状态”。路径编码问题可在ASCII临时路径验证，但不把改名所有项目写成通用要求。

## 验证与故障证据

分别报告：配置审查、生成、功能仿真、OOC/顶层综合、实现/STA、下载身份、板测。OOC生成DCP不等于功能仿真；综合后的时序/CDC报告不等于完成布局布线或板级电气验证。

仿真按实际接口接受条件记账，用独立参考结果检查顺序、丢失/重复、延迟、复位和边界。参考队列要处理同拍读写与已约定的读延迟，不能把错误检查器误判成DUT失败。需要增强信心时加入针对性的负控，确认检查器能抓到注入错误；不要只搜索日志PASS或复写实现公式。

CDC和约束检查依据实际跨域结构及模块契约。工具报告可能含已有的有据例外，不要求所有警告清零；新增问题需解释原因与覆盖边界。厂商模块也可能要求特定时钟、复位顺序和约束，不能因“成熟IP”忽略它们。

重复失败先区分配置错误、接口适配、工具环境、模块不适用和检查器错误，再决定修复或重新选型。只有用户当前任务涉及板测时才安排相应操作，技能使用本身不授权下载或连接硬件。
